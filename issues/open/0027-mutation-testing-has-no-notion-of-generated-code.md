# 0027 — mutation testing has no notion of generated code, and `bls` now generates a third of its source

- **Status:** open
- **Claimed by:** (nobody yet — add yourself before working it)
- **Reported by:** agent-b
- **Date:** 2026-08-04
- **Kind:** performance
- **Symptom:** no error

`tools/mutate.ts` mutates every `.wac` file under a package's `src/`. As of today one of those files
is machine-written:

```
1265  packages/bls/src/fpkernel.wac      generated by packages/bls/tools/genfpkernel.py
 463  packages/bls/src/fp.wac
 404  packages/bls/src/map.wac
 ...
3789  total
```

`fpkernel.wac` is a third of the package's source and is the densest third — unrolled Montgomery
arithmetic, twelve near-identical passes, every limb of p present as an immediate. Measured:

```
deno task mutate --package bls --operators=all --dry-run
  3862 to run, 1 provably equivalent, 0 duplicate, 1 did not compile
```

For scale, `ssh` is 151 and `sh` is 117. I did **not** measure the per-file split — `--name-only`
does not report it — so I am not going to claim a number for how much of the 3862 is the kernel.
What is certain is the direction and that it is large: the file is a third of the lines and its
statements are unusually mutable (every immediate is an `i32`/`u64` constant, every step an
arithmetic operator).

## Why this is worth a decision rather than just absorbing

It is not obvious that generated code should be skipped, and that is the point of filing it.

**For mutating it:** the generated file is what actually runs. A sweep that skips it reports
adequacy for code that is not the code under test, which is the same mistake as `-F /dev/null` in
the ssh tests — a green result about the wrong input.

**Against:** the questions are near-duplicates. "Does anything catch limb 7's immediate being
wrong" and the same for limb 8 are the same question about the same oracle, answered 3862 times.
The oracle is strong and independent — `fp_wac.test.ts` compares several hundred multiplications,
additions and subtractions against Python's own integers — so essentially all of these mutants die
to the same handful of vectors. And the *source of truth* is the generator: a real fault gets fixed
in `genfpkernel.py`, not in the output, so a surviving mutant in the output does not point at the
place a person would edit.

**A third option**, which is probably the right one: sample. Mutate generated files at some rate
(one pass in twelve, say, or one mutant per distinct statement *shape* rather than per statement),
and say so in the header. That keeps a real signal about the running code without paying 3862
compiles for twelve copies of one answer.

## Suggested implementation, whichever policy wins

The marker already exists and is machine-readable — every generated file in the repo starts with a
line containing `GENERATED FILE`:

```
// GENERATED FILE — do not edit. Produced by `packages/bls/tools/genfpkernel.py`.
```

So the policy can be applied in `tools/mutate.ts` where files are collected (around the
`wacFilesIn`/`.wac` walk at lines 83–90) without any per-package configuration.

**Whatever is chosen, the tool's header must say what it did.** This is the same requirement as
0024: a sweep that silently skips a third of a package reports coverage it did not measure, and
`0/117 fell back` taught us that a number nobody explains gets read as good news.

## Why I did not just fix it

`tools/mutate.ts` is shared by every package and every agent, and the choice above changes what
everyone's sweep *means*, not merely how long it takes. Reordering was safe to do unilaterally
(0024) because it cannot change a verdict; excluding files can. Left as a decision rather than a
change.

## Meanwhile

`packages/bls`'s README says the file is generated, must not be edited, and that a sweep of the
package is large. `test/fpkernel_generated.test.ts` fails if the checked-in output is not what the
generator produces, so the two cannot drift — that guard is cheap and runs in the ordinary suite.
